# VibraPilot v1.0.6.7 — Windows SQLite concurrency verification correction

## Scope

This follow-up is limited to the Windows `TaskRuntimeStore` multi-worker write-contention failure reproduced by `test_four_worker_threads_persist_independent_results_without_cross_run_leak`. No feature, selector, browser workflow, licensing protocol, Browser Settings or unrelated UI behavior is changed.

## Root cause

The stress path performed three independent SQLite write transactions per recipient (`save_item`, `upsert_result`, `save_progress`) from four worker threads. WAL permits concurrent readers but only one writer. On Windows, competing writers could remain inside SQLite's busy wait long enough to exceed the 15-second test join window; the still-running thread then retained a database file handle and `TemporaryDirectory` cleanup raised `WinError 32`.

## Correction

- `TaskRuntimeStore` now serializes in-process write transactions before SQLite's WAL writer lock.
- The high-frequency recipient hot path persists item state, authoritative result and run progress in one transaction via `persist_item_result_progress`.
- `AutomationWorker._save_runtime_item` and the pre-Send crash marker use that atomic persistence API.
- SQLite synchronous durability is not weakened.
- The concurrency regression test exercises the production atomic path while retaining the 15-second completion requirement.

## Preserved

Licora API v2, `LicenseManager`, Razorpay selectors/Send sequence, Test Mode/security behavior, Browser Settings, ActivationPage, branding and unrelated worker methods remain frozen.
