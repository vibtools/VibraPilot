# VibraPilot v1.0.6.5 — Production Multiple-Task / Long-Run Stability

Update scope: `VP-PROD-MT-LR-001`  
Official baseline: `VibraPilot_v1.0.6.4_Latest_Updated_Baseline.zip`  
Baseline SHA-256: `ea65bd89d908c5db8edfcf01e6b7c5e11410ffe57a98044f9e8913477f9e89e6`

## Scope

This release changes only Multiple Task runtime stability, long-running worker lifecycle, recipient/result integrity, recovery and release/runtime-data hygiene. The Licora API v2 protocol, P-256/RS256 implementation, `LicenseManager`, Razorpay Share Invite selectors and Send sequence, Test Mode/security rules, `ActivationPage`, Browser Settings contract, branding and Vib Tools design foundation remain frozen.

## Runtime persistence and recovery

A new local `TaskRuntimeStore` persists task runs in `AppData/task_runtime.sqlite3` using Python `sqlite3`. Each task run receives a unique `run_id`; recipient state and the latest authoritative result are keyed by `run_id + item_index`. The store uses WAL mode, foreign keys, a busy timeout and short-lived committed connections so multiple worker threads can safely persist independent task state.

Task progress is saved after finalized recipients and at approved timed autosave intervals. `auto_save_interval` is measured in **seconds**; `0` disables timed autosave but does not disable immediate persistence of finalized recipient outcomes. Compatibility JSON checkpoints use temporary-file write, flush/fsync and atomic replacement. `batch_size` also defines an explicit SQLite WAL checkpoint boundary, while recipient processing remains sequential.

If the runtime SQLite file is positively identified as malformed/not-a-database at startup, it is preserved under a `.corrupt-<id>` quarantine name and a clean store is created; generic lock/permission/I/O database errors are not treated as corruption and are not silently replaced. Unsupported run schema versions are not offered for recovery.

On startup, incomplete runs can be restored into the existing Tasks workspace. Recovery never opens a browser or starts sending automatically. The operator must restore the task, open the browser, complete login/Test Mode verification and explicitly resume. If a Send click occurred without a definitive success/rejection, the run is restored in manual-review state and automatic retry remains forbidden.

## Sequential batch boundaries

`batch_size` is now functional but does not introduce parallel recipient sending. It defines bounded sequential checkpoint boundaries. The existing one-recipient-at-a-time Share Invite workflow remains unchanged.

## Input reconciliation

Data import now records source rows, valid rows, invalid rows, duplicates removed and accepted rows. The existing validation rules remain authoritative; invalid recipients are not silently converted into valid data. Task UI status/logging exposes the reconciliation summary after load.

## Worker and Browser Context stability

Successful and confirmed-failed finalized recipients now both contribute to the existing item/time Browser Context recycle counters. Paused, blocked, ambiguous and interrupted items do not advance safe recycle accounting.

Workers expose a completion event after browser cleanup. Task removal, logout and application close no longer discard the live worker reference merely because an 8-second wait window elapsed; the operation is held/cancelled until cleanup completes.

## UI event backpressure

The shared UI queue is bounded to the approved capacity of **4096**. Critical outcome/security/browser/lifecycle events use backpressure rather than silent loss. Replaceable high-frequency progress/status/log events may be dropped under sustained queue pressure. The UI processes at most **250 events per timer tick**, preserving event-loop responsiveness while leaving authoritative recipient results in the runtime store.

## Reporting

Reports now represent one current authoritative outcome per recipient/run item instead of treating `processing` and final events as separate result rows. The visible table remains bounded to recent records, while CSV/Excel export reads the full persisted ledger. Existing status/search filters remain and a Task filter allows All Tasks or a specific slot.

## Multiple-task guards

`max_concurrent_tasks` is a functional App Setting with approved default **4**. Users may retain additional task cards, but more than the configured number of active browser workers cannot be launched concurrently. If persistent context is enabled without dedicated per-task profiles, a second task is blocked from claiming the same profile path while another worker owns it.

## Release boundary

Release/delta packages must not contain runtime/private/cache paths including `AppData/`, `FailedData/`, `Reports/`, `Logs/`, `project/`, `__pycache__/` or `.pytest_cache/`. Runtime data remains local and must be preserved when applying a source delta to an existing working installation.
