## Required invariants

1. Build host is Windows x64 with Python 3.12.
2. Nuitka is pinned exactly to 4.1.3.
3. Compiler mode is standalone OneDir, not onefile.
4. PySide6 packaging uses the Nuitka PySide6 plugin.
5. Playwright Python/driver runtime is present through Nuitka 4.1.3's built-in Playwright standalone support; `--playwright-include-browser=none` explicitly prevents browser inclusion.
6. `chrome.exe`, `chromium.exe`, `headless_shell.exe`, `ms-playwright`, and `.playwright-browsers` are rejected from the portable payload.
7. WiX/MSI payloads are rejected.
8. `config/settings.defaults.json` and frozen UI tokens resolve from the packaged root.
9. Existing PyInstaller source compatibility remains intact; the historical `build.py` is not replaced in this release.
10. Runtime business logic, browser launch policy, workflows, licensing protocol, persistence schemas and UI behavior remain frozen.

## Windows owner acceptance required before public tag release

- Extract into a clean folder and launch `VibraPilot.exe` without Python installed.
- Validate licensing and restart behavior.
- Install/activate external Share Invite and DMARC `.vpworkflow` packages.
- Open verified system Google Chrome with managed profiles.
- Run a controlled DMARC flow and a controlled Share Invite Test Mode flow.
- Confirm Logs/Reports/AppData behavior and clean shutdown.
- Record ZIP size, SHA-256 and largest-file inventory from the GitHub Actions artifact.

A manually dispatched GitHub Actions candidate is not a public release until these owner checks pass. Tag publication is additionally blocked unless the tag is exactly `v{AppConfig.VERSION}`.

## RC startup observability correction

The first real `workflow_dispatch` build (`32048312168`, job `95441285784`) proved that source verification, Nuitka compilation, OneDir packaging, checksum verification, and the no-Chromium/no-WiX policy all work on the pinned Windows 2022 runner. The resulting candidate contained 827 files and produced a 116,446,695-byte ZIP with SHA-256 `90f95746a381d089d4ad3fe399f0087cabcba28ea9d26abc680cc95d3c0ad65c`.

The executable then exited with code 1 during startup smoke. Because that candidate used `--windows-console-mode=disable` and the workflow did not capture forced stdout/stderr or application logs, the failed run contains no Python traceback. The exact runtime exception is therefore intentionally not guessed.

The correction remains packaging/verification-only: manual RC builds enable Nuitka forced stdout/stderr capture, smoke execution removes inherited `PYTHONPATH`/`PYTHONHOME` and sets `PYTHONNOUSERSITE=1`, and startup diagnostics are uploaded on failure. Tag builds retain the normal GUI no-console behavior and public release remains blocked unless the startup smoke passes.


## Second RC forensic closure

Run `32056816056` / job `95468779983` again passed source tests, Nuitka 4.1.3 compilation, OneDir creation and portable forensic verification. It produced 827 files, 324,248,255 uncompressed bytes and a 116,450,399-byte ZIP with SHA-256 `d2afb06bacb807987ef3f5e010b801f644a4127997ee0b9ca9331ab9e41e0f5a`.

The new diagnostics artifact `9297920798` (artifact ZIP SHA-256 `4e26c5b3f9683cd3422e178d1cd7472ac8057286f6bf683880aca3b772fe9ec0`) captured the exact startup failure:

`RuntimeError: Settings defaults could not be loaded: ...\release\config\settings.defaults.json`

The data file was present inside the verified portable folder. The fault is therefore runtime-root resolution, not missing packaging, Qt plugins, Playwright driver, Chromium policy, WiX/MSI, or compilation. v1.0.6.38 corrects that single root-selection defect.
